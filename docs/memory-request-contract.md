# 記憶請求與壓縮流程核對

核對基準：2026-10-31，main `1983472`，以及本次共用額度／完成狀態修正。

## 預算分層

| 層級 | 作用 | 不可混用 |
| --- | --- | --- |
| 開局第 5 步 | 經濟／均衡／長篇設定保留輪數、整理間隔、上下文壓力參考值 | `memory.maxContext` 不是模型容量，也不是摘要輸出額度 |
| 記憶任務 | 各整理器明確要求 `maxOutputTokens` | 成本包裝層不得再一律截成 1,800 |
| 模型協定 | 轉為 Gemini `maxOutputTokens`、OpenAI 相容／Anthropic `max_tokens` 等參數 | 模型能力與供應商限制仍然有效 |
| 夜灣燈火 | 前端與 Worker 執行已開放模型、輸出、餘額與傳輸上限 | 不能以提高 BYOK 數字繞過後端限制 |

現有第 5 步預設：經濟 12 輪／16,000 參考預算／8 輪間隔，均衡 20／32,000／4，長篇 40／64,000／6。這些值影響原文保留及整理時機；不會為模型設定官方上下文容量。

## 功能分工與寫入條件

| 功能 | 來源與用途 | 本次修正後的輸出要求 | 成功寫入 |
| --- | --- | --- | --- |
| 自動記憶 | 已完成的舊對話＋既有摘要；逐批整理 | 8,192；既有 Gemini 3 摘要策略為 16,384 | 驗證完整結果後才更新摘要與覆蓋游標 |
| AI 整理 | 玩家選定範圍，產生必記事項草稿 | 1,400 | 完整草稿供玩家預覽；玩家確認後才寫筆記，不推進自動游標 |
| 劇情檔案 Canon | 分段證據提取、分層合併與玩家確認 | 提取 2,200；中間合併 2,600；最終合併 3,200 | 完整結果才替換草稿；確認前不取代正式檔案 |
| Context Pack | 分段整理、分層合併、保存續作進度 | 2,200 | 完整分段才保存 checkpoint；失敗不跳過該段 |

以上為呼叫端要求，並非保證每次使用或供應商允許的 token 數。共用成本層保留明確額度，總故事預算仍可在送出前拒絕請求；傳輸層保留其安全上限。

所有上述整理器共用 `Chat.memoryCompletionError` 的完成狀態規則。即使回傳可解析的 JSON，`MAX_TOKENS`、`length` 或內容阻擋也不能視為完成。自動摘要保留既有有限次縮小批次重試；手動工具顯示失敗並保留原稿或已完成進度，不新增隱藏的付費重試。

## 這次找到的問題與測試缺口

`cost-control:budget` 原先對所有 `__memoryTask` 再套 `min(requested, 1800)`，位於路由之後、傳輸之前。只測整理器傳入的 config 無法發現最後請求被改小；舊整合測試甚至將 1,800 當成預期值。

本次測試驗證最後序列化的請求，涵蓋五種傳輸、六種任務額度、四種包裝層安裝順序，以及三種協定的自動摘要成功／截斷重試／失敗保留。模型呼叫以網路邊界的測試回應取代，沒有使用玩家金鑰或付費資料。

## 開源方案對照與後續架構邊界

- [SillyTavern Summarize](https://docs.sillytavern.app/extensions/summarize/)：獨立摘要輸出預算，批次容量扣除摘要指令、舊摘要與預留輸出，並保留摘要回復能力。適合夜灣故事聊天流程的參考。
- [Letta compaction](https://docs.letta.com/v1-sdk/messages/compaction)：近期原文與較早摘要分層，摘要模型與設定可獨立配置。
- [Mem0](https://github.com/mem0ai/mem0)：長期事實抽取與檢索，適合評估事件記憶的檢索層。
- [LLMLingua](https://github.com/microsoft/LLMLingua)：提示文字壓縮；不能單獨取代來源證據、角色知情權限、存檔及摘要覆蓋進度。

本次採取各任務持有預算、完整結果才提交的共用規則，沒有安裝或移植上述框架。後續若改為依模型能力配置預算，應由模型登錄與協定轉接層提供上下文／輸出／推理額度資料，整理器只描述任務需求；未知能力不能假裝已知。既有 Gemini 3 的輸出及 thinking 特例尚未在本次全面改成能力登錄。

仍需獨立設計的範圍：AI 整理「全部對話」目前是單次請求，並非自動摘要的分批管線；必記事項仍會消耗每輪輸入空間。修正隱藏輸出限制不代表任意長度的輸入都能送出，也不代表模型不會遺漏或誤記。自動摘要、檢索、提示快取與文字壓縮應分別驗證，不以提高單一上限取代它們。
