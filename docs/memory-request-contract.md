# 記憶請求與壓縮契約

本輪整合以 PR #891 的共用額度修正為基礎。`js/memory-core.js` 提供共同路由解析、模型能力與任務預算、來源分批、完成狀態驗證及文字逐批續作；網路與保存仍由既有夜灣模組負責。

## 共同流程

1. 依故事設定選擇沿用主模型或獨立記憶模型，建立本次任務的連線快照。舊 `summaryModel` 字串不再覆蓋實際路由；不同端點不得借用主模型金鑰。
2. 讀取模型登錄、連線明示能力或玩家已取得的服務商模型清單；依任務選擇輸出預算。
3. 先保留指令、既有摘要、輸出及安全空間，再計算來源批次。合併也以整個實際提示計算；已超預算時先縮小批次或拒絕送出。
4. 經原有 API 包裝層與傳輸層送出，繼續執行總故事預算、燈火餘額、金鑰隔離、使用量與傳輸限制。
5. 驗證供應商完成狀態、解析內容及故事／來源所有權。JSON 可解析不代表 `MAX_TOKENS` 或 `length` 是成功。
6. 僅在有效結果完成後保存進度。草稿仍依原有玩家確認流程才成為必記事項、正式 Canon 或摘要包。

## 第 5 步與模型容量

第 5 步的經濟／均衡／長篇設定，控制保留輪數、整理間隔與故事上下文壓力參考值。`memory.maxContext` 不當作模型官方容量，也不直接壓低記憶輸出。

共同預算以 UTF-8 bytes / 2 作保守的 token 估算，不等同任何服務商 tokenizer 或帳單。未知能力時，每次整理的輸入估算目標為 12,000 tokens；這是夜灣策略，不能宣稱未知模型一定支援。服務商回報錯誤時保留資料。

已知總上下文容量時，輸出最多配置其 40%，再遵守已知輸出上限；輸入另扣輸出和 10% 安全空間（128～1,024 tokens），並受整理輸入策略及已知輸入上限限制。所有訊息仍須通過 180,000 bytes 的記憶預檢；後續正式傳輸層維持自己的限制。

## 模型能力與任務策略

模型登錄的邏輯模型／路由、或連線物件可提供：

```json
{
  "capabilities": {
    "contextWindowTokens": 32000,
    "maxInputTokens": 28000,
    "maxOutputTokens": 4096
  },
  "memory_policy": {
    "inputTokens": 12000,
    "outputTokens": {
      "summary": 8192,
      "notes": 4096,
      "canon-extract": 2200,
      "canon-merge": 2600,
      "canon-final": 3200,
      "context-pack": 4096
    }
  }
}
```

以上只是欄位範例，不是任何特定模型的能力宣告。`capabilities` 是可用上限，`memory_policy` 是夜灣希望採用的任務策略；要求仍會被已知上限約束。新增模型不必在整理器內加入模型名稱條件。

既有 Gemini 3 的 16K 摘要／low thinking 設定已搬到登錄中的 `memory_policy`。Gemini 協定轉接器只在任務明示 `thinking` 時帶入對應參數；其他模型不憑名稱猜測思考參數。燈火 Worker 的供應商能力與允許清單仍由後端獨立管理。

玩家使用既有「從帳號取得模型」功能時，模型清單會保留可辨識的能力欄位，按端點、協定和模型 ID 索引，不存金鑰、不增加自動查詢。OpenRouter 的 `context_length`／`top_provider.max_completion_tokens` 與 Gemini 的 `inputTokenLimit`／`outputTokenLimit` 分別正規化；Gemini 輸入上限不誤當成輸入加輸出的總窗口。清單沒有回報的能力不自行補造。

## 各工具與保存條件

| 功能 | 分批及預算 | 保存與確認 |
| --- | --- | --- |
| 自動記憶 | 保留近期原文，僅處理已完成舊回合；既有摘要與全部指令一起預檢；截斷後有限次縮小批次重試 | 成功才推進 `summarizedUntil`；失敗保留摘要、原文與事件索引 |
| AI 整理筆記 | 任選來源逐批壓縮為可續接摘要；每次最多 8 批，預估多批時先說明費用並確認 | 每批保存 `memoryRefineJob`；重載或追加未覆蓋來源後，可重用相同設定且來源前綴未變的成功進度；全數完成才更新 `memoryRefineDraft`，玩家另按寫入；不推進自動游標 |
| 劇情檔案 Canon | 完整證據提取、依輸入容量分組合併、最終校驗；各階段有獨立任務預算 | 每批及合併保存 `canonJob`；相同來源／模式／規劃可續作；最終只產生草稿，玩家確認後才成正式資料 |
| Context Pack | 分段規劃也扣除指令與輸出；合併組數依實際提示容量決定 | 成功才推進 chunk／merge 游標；沿用既有存檔及重載續作入口 |
| JSON 修復 | 沿用同一連線快照、獨立 1,400 輸出要求，預檢實際修復提示 | 不替來源補故事；完成驗證與來源所有權規則同樣適用 |

AI 筆記的基礎預留輸出由 1,400 改為 4,096；Context Pack 由 2,200 改為 4,096。實際使用量取決於模型輸出，服務商上限與燈火預留規則仍有效。批數是成功整理批次，不保證每批只有一次 API 呼叫：既有 JSON 修復仍可能另有模型用量。

每故事／每工具均防止重複啟動。遲到的回覆不能寫入另一故事、被修改的來源或被取代的草稿；原始對話不刪除。重載後續作不保存 API Key，玩家仍須依原有安全流程重新連接。

舊 Context Pack work v1 可能在合併失敗前已提前推進 merge 游標。轉為 v2 時保留成功的分段提取結果，重新合併無法證明覆蓋的部分，避免靜默跳過來源；既有合併可能需要重做一次。

## 開源參考與實作範圍

- [SillyTavern Summarize](https://docs.sillytavern.app/extensions/summarize/)：摘要輸出與聊天額度分開；可整理來源須扣除指令、前次摘要與預留輸出。本輪把這個規則落成共用規劃與送出前驗證。
- [Letta compaction](https://docs.letta.com/v1-sdk/messages/compaction)：近期原文／較早摘要分層及獨立摘要設定；夜灣保留既有分層，讓各整理工具統一使用連線與任務預算。
- [Gemini Models](https://ai.google.dev/api/models) 與 [OpenRouter Models](https://openrouter.ai/docs/api/api-reference/models/get-model)：能力欄位語意的依據，能力值以實際服務商回報為準。

本輪是夜灣既有架構的整合，沒有安裝上述框架，也沒有新增 Mem0 向量服務或 LLMLingua 壓縮模型。既有事件記憶、Canon 的相關條目檢索、角色知情權限、必記事項和提示快取繼續保留；不是所有記憶都要每輪全量送出。

必記事項仍是玩家明確選擇常駐的內容，會消耗輸入空間。模型摘要可能遺漏或誤記；本輪不宣稱無損語義壓縮。可保證的是分批來源不因字串切割而漏字、成功進度才前移、失敗保留原資料，以及只有玩家確認的工具草稿才正式寫入。

## 驗證

`tests/memory-orchestration-core.cjs` 覆蓋未知模型能力、服務商能力回報、端點隔離、預算扣除、Unicode 來源完整性、限制每次批數、已付費進度續作及遲到回覆阻擋。整合測試驗證最終序列化參數；Canon／Context Pack 測試包含中途合併失敗與保存後續作。瀏覽器測試涵蓋第 5 步、手機與桌面、長篇整理重載、草稿確認及原始對話／自動游標保留。測試在網路邊界模擬模型，沒有使用玩家資料或付費 API。
