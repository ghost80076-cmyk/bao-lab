## 原始範圍與退出條件

原始優先順序的兩項 P0 是：

1. **模型路由、計費與請求生命週期**：避免錯 Provider、重複記帳／結算與不安全重試。
2. **本地資料、故事存檔與備份**：保存資料完整性，修改後能正確讀取、還原與備份。

流程仍是「盤點 → 補回歸保護 → 單一問題拆分合併」。本報告是第三階段後的結案核對，不以後來發現的每個改善機會無限延長 P0。

退出條件：原始工程契約有對應回歸證據、相關腳本無失敗、同一主線 CI／部署成功、已知相容限制明列。以此範圍結案後，新發現的可重現資料損壞、錯路由或重複扣款仍須重新升級為 P0；本結案不阻止事故處理。

## 已知限制與待確認事項

| 項目 | 分類 | 明確邊界 |
| --- | --- | --- |
| 正式錢包與供應商帳單對帳 | 營運待確認 | 本輪沒有查正式帳戶；不能據此關閉過去的實際金額異常事件 |
| Hosted 客戶端 idempotency key／結果重播 | 後續能力 | 瀏覽器目前以不自動重試付費模糊錯誤降低重複扣款風險；尚未承諾跨 HTTP 重送重播相同結果 |
| 缺少 Web Locks 的 localStorage 備援 | 相容性限制 | 單 key 提交仍原子；不同分頁的讀改寫不保證互斥。主流測試環境的 Web Locks 路徑已驗證 |
| 同章節同時修改、共用自動存檔 | 既有衝突策略 | 最後提交取代；目前分頁位置已隔離，但重載仍依實際載入的共用自動存檔，沒有逐頁獨立持久化進度 |
| 刪除標記保留與舊歷史資料缺損 | 後續維護／歷史限制 | 尚無 tombstone 清理策略；已被早期版本丟棄的欄位、覆寫的時間不能推回原值 |
| 舊式直接覆寫 API.send 的第三方擴充 | 相容性限制 | 固定 stage 排序在具名 segment 內成立，不跨不透明 legacy 邊界 |

以上不是新增 P0 工程阻擋項，也不是已實作的新能力。若產品要擴大承諾，須另立明確驗收，而不是把現有基線寫成全面保證。

## P1 交接與停止線

P0 結案後，回到原始 P1：

1. **記憶、世界書、狀態更新的責任邊界**：盤點正文後更新、同模型合併與獨立 helper 的 owner、等待／取消、重入及持久化時點。已完成的 14-stage 路由／計費保護作為既有基準。
2. **核心呼叫鏈剩餘耦合**：以目前主線重新盤點 App／Chat／GameState 的 hook 與直接覆寫；先列單一問題及驗收，再拆分。已收斂的訊息 writer／decoder 與分支提交不重複改造。
3. UI／CSS、Workflow 去重與舊文件仍屬原 P2，保留原優先序。

本次僅新增結案文件與證據，不修改產品程式、正式帳務或資料格式。下一批工作以 P1 身分追蹤，不再將這串儲存延伸重構持續標作 P0 收尾。
