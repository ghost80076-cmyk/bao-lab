# 請求追蹤、上下文檢視與 NPC 個別時間線

## 使用入口

- 管理後台 → 玩家 API 消耗明細：成功／失敗請求的生成 ID、路徑、生成 POST 次數、耗時、錢包帳本金額核對。回報差額只在同筆請求有美元實扣及 Provider 回報成本時提供。
- 故事總覽 → 更多故事設定 → 上下文狀態 → 進階 Token 說明與請求檢視：查看最近一筆故事請求送出前的訊息與世界書／事件記憶選取結果。
- 故事總覽 → 更多故事設定 → NPC 個別時間線：查看人物有來源的認知，並明確安排離場日程。

## 請求與帳務

`api_request_traces` 為補充性表格，以 `request_id` 關聯既有 `api_usage` 與 `wallet_ledger`。表格建立及寫入沿用 runtime `CREATE TABLE IF NOT EXISTS`，不需破壞性遷移；新增模組列入 Worker 部署 manifest。寫入失敗不阻擋既有退款／結算，不保存正文、提示詞、憑證或上游 raw error。成功、空正文、用量未確認和傳輸失敗均嘗試寫入。舊請求沒有 trace 時顯示未知。

`attempt_count` 計算實際生成 POST，包含既有 relay 拒絕格式後的相容性重送；用量補查 GET 不算生成重試。這次沒有新增自動 fallback 或付費重試。

`wallet_check` 僅核對同一玩家、同一 request 的 usage 帳本金額與實扣，識別重複／缺失／金額不一致；不是供應商正式帳單核對。`reported_margin_microusd` 是 Provider 回報成本與玩家實扣的差額，不宣稱是含匯差、稅費及其他帳單調整的利潤。成本缺失與明確的 0 分開處理。舊制 credits 不換算美元。

營運待辦 O1 仍需正式供應商帳單與 D1 正式明細，才能完成逐筆核對。未提供正式帳單時，所有列的 `invoice_check` 都是 `not_reconciled`。

## 上下文檢視

API 管線第 125 階段擷取訊息，位於 Prompt 轉換與合併狀態契約之後、本機／Hosted transport 之前。此快照是應用層訊息，服務商協定序列化仍可能重組 system 或 cache 設定。固定前綴候選不等於已命中快取；每層只顯示字元數，Provider 輸入／輸出／快取讀取顯示實際回報，未知不推算。

世界書與事件記憶由實際選取演算法回報 included、knowledge、evidence、retracted、duplicate、irrelevant、budget 等原因；分數是既有關鍵字排序分數，不是 embedding 相似度。每層最多顯示前 150 筆決策；沒有重新執行一次選取來猜測結果。平台舊版角色卡內嵌世界書、Canon、各種提示詞 wrapper 仍以實際訊息正文檢視，尚未逐一附加條目級排除原因。

每個作用中 state 只保留最近一筆故事請求，最多顯示 200000 字元；不存入存檔、不自動匯出、不上傳遙測。輔助模型與連線測試不覆蓋故事快照；原文更改、回退與分支切換會檢查來源，重新載入或 reset 後須再送出。

## NPC 時間線第一版

有來源的個人經歷沿用 episodic memory 的 evidence 與 knowledge，保留 witnessed／told／rumor／inferred，不因玩家看過事件而讓所有角色知情。現有知情表最多讀取最近 50 筆有效事件；這不是另一套全文記憶索引。

離場日程由玩家明確建立，使用既有世界時鐘相對分鐘。固定日程只有在時間跨過期限且人物明確 `away` 時才完成；在場、未知或需要抉擇的事項皆進入 ready 待判定，不自動變成結果。待判定日程可取消；當既有主模型或狀態模型從本次故事正文提取到有來源的結果，可透過結案 PATCH 記錄。沒有自行編造「吵架」「接受邀請」等事件。

日程寫在既有 `GameState.current.npcTimeline`，隨既有完整 state 備份、還原、分支與 revision snapshot 保留。來源訊息變更後不再作為有效經歷；已完成項目不會重複執行。不改動 NPC 位置、性格或玩家狀態。最多保留 50 個未完成項目與 70 個歷史項目。

個別日程只在共享請求的所有現場角色都能讀取時加入動態上下文，沿用現有 audience；不將時間線整表塞給模型。沒有逐 NPC AI 呼叫，也沒有新建另一套世界時鐘或記憶系統。

## 驗證

`request-observability-core.cjs` 使用 SQLite 執行實際管理 JOIN，驗證帳本隔離、差額與未知成本；另有上下文管線及 NPC 分支／來源測試。`request-observability.yml` 執行核心回歸及手機／桌面瀏覽器操作並保存截圖。這些測試不代表已完成正式帳單核對。

## 第二階段：待判定事件結案

狀態契約可選附加 `npc_timeline.resolve`，每筆只有既存日程 ID 與 8～300 字元的逐字故事引文。只有到期、待判定、來源有效，且目前共享角色全都能讀取的日程才會提供給模型；每輪最多六筆。沒有可處理日程時不附加這份契約。

引文必須包含該 NPC 正式姓名或已登錄別名，並能在本次整理範圍內、已保存的 assistant 故事訊息找到。開場、玩家輸入、狀態 JSON、無關舊輪次與捏造引文皆不能作為來源。只保存逐字引文、來源訊息 ID／簽名及結案時的相對分鐘，不用模型另寫一份摘要。角色拒絕、失敗也是可能結果。

程式驗證的是引用與來源，不保證自然語言的完成／假設語意能被硬性證明；狀態判斷仍由既有模型負責。界面保留「重新待判定」。原文編輯或回退後，來源失效的結果標示「來源已變更」，不再提供為模型經歷；分支沿用各自的 state 與對話來源。

共用主模型時使用同一份 BAO_STATE 附錄，沒有補發請求；使用獨立狀態模型時沿用原有批次整理流程與間隔。`npc-timeline-resolution-core.cjs` 驗證來源、範圍、分支、角色隔離及一次呼叫；瀏覽器測試涵蓋送出故事後結案與重新待判定。
