# P4｜選用章節召回：每輪預算與來源驗證

日期：2026-11-07。此功能建立在 #939（Token 量測）、#940（合成成本對比）、#941（章節索引與知情控制）及 #942（玩家審閱／保存）之上。它**不是**自動章節蒸餾，也**不等於**每輪 Token 立即節省。

## 啟用方式與資料歸屬

- 記憶工作台「章節回憶」的開關由玩家明確選用；預設關閉。
- 開關記錄於目前故事的 `GameState.current.chapterMemorySettings`，採 `BAOMemoryCore.commitState`、共享工作鎖、儲存 flush 與讀回驗證。關閉後不刪除已保存章節。
- 備份／匯出沿用既有故事 state；不增加全域偏好、伺服器資料庫、API 請求或模型整理費用。
- 選用模組載入失敗時，故事照常進行；開關不應允許啟用未就緒功能。

## 每輪召回門檻

`BAOChapterMemoryRecallCore.plan` 僅在全部條件成立時提供至多一章：

1. 玩家於目前故事啟用、模式為智慧整理、事件知情檢索未被停用；
2. 普通故事最新玩家輸入，排除帶來自其他快照的 `request.contextMessages`／非目前 `request.sourceMessages`，防止重生成、回溯時混入另一個來源；
3. 已成功建立摘要，且章節來源 **完全早於 `Chat.contextGuard.rawStart` 與 `Chat.summarizedUntil`**，避免把原文仍在 Context 的章節重複塞入；
4. 章節與最新輸入本地關鍵詞相符，且每次 `BAOChapterMemoryCore.recall` 都驗證核准狀態、原文 ID／內容指紋和角色知情；沒有核驗者就停止；
5. 正文提示詞已含相同章節全文時不重複；
6. 上一輪 `lastStoryPromptTokens / maxContext` 已達 73% 不召回；另用保守位元組／2 粗估，要求加入後低於設定 Context 75%；
7. 單輪最多一章、章節區塊至多 900 字元、**額外輸入粗估不得超過 450 Token**；超限就整章跳過，不截斷事實，也不擠掉玩家原文。

召回區塊只附加到當輪最新 user 訊息前方，**不動 system 固定前綴、其他記憶、原始聊天或玩家輸入本體**。這是本機查找，並無新的 Provider 呼叫。當模型接收資料時，僅能把章節視為舊事來源，不可覆蓋更新原文、Canon 或目前 NPC 已知內容。

## Token 與費用界線

- UI 顯示「上一輪額外輸入粗估 Token」，僅為 `BAOMemoryCore.tokens` 的位元組估算，不是 Provider 實際分項 Token 或扣費。診斷只存在記憶體 WeakMap，不保存原文或上傳。
- 啟用後有符合條件的章節時，**每輪輸入可能增加**。目前只是有界補足長期資訊；總成本還應納入每輪輸入／輸出、快取讀寫、原有摘要與任何未來蒸餾成本。
- 新功能沒有取代原有智慧摘要，也沒有產生任何聲稱省 Token 的實測統計。

## 驗收與分支依賴

- Node：100／500／1,000 輪來源有效、核准知情、非公開角色混合場景、來源編輯、重生成、總預算、未啟用／非 smart／近期原文重疊、保留固定 Prompt 前綴。
- 工作台保存：開關提交、讀回、寫入失敗與驗證失敗回滾，沒有有效章節不能啟用。
- E2E：手機 390px，手動章節審閱後明確啟用、無 API 呼叫的 `App.buildMessages` 比對、關閉後原 Prompt 不受影響；保留 #942 的手機與桌機完整存檔／回溯驗收。
- 此 PR 從 #942 的 head 分支建立。合併前應依 P0 → P1 → P2 → P3 → P4 整理重疊差異並重新跑完整 CI，不能直接將重複檔案覆蓋主線。

後續只有在真實故事取得足夠的有來源召回品質與總成本比較，才考慮更進一步的章節自動整理／多章蒸餾；不得默默新增付費整理任務。
