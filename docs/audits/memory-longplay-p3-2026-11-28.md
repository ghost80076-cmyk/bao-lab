# P3 長篇記憶量測 — 停止增加排序規則

以 14945a6f26cbc49e857e6238c567d95bf001b16e 為基準；比較 P1b 後、P2a 前的固定 commit ae6d305e14d250a15c80e8eabe5d281186b6da2b 與現在的事件召回 core/wrapper。使用完全相同的合成索引與來源、固定 stub base prompt、實際 wrapper 輸出。不是另一套記憶機制；不修改任何 runtime、預設、存檔或作者設定。與既有 P0 76 案及分層成本 lab 互補。

三組合成情境（上下文承接、登錄別名、角色後續知情更新）在 100、1000、5000 輪及 60、600、1000 筆索引測試，每組五筆同題干擾。驗收針對指定目標名次、來源、權限、去重／輸出限制、無關／停用／full、預設模式相容、改寫、回溯與零模型呼叫。1001 筆容量邊界明確量測最舊事件移除：不能把原文仍在誤認為索引仍可召回。測試不要求所有干擾事件消失；其他召回數獨立列出，並非任意真實故事精確率。

每個主要情境 warm-up 後 12 次 wrapper 量測 P50/P95、歷史及索引 JSON UTF-8 bytes、實際注入 bytes 與現有 BAOMemoryCore.tokens 粗估差值，記錄 Node 版本、平台、來源雜湊。不用不穩定 runner 延遲作硬性門檻；同環境比較而非手機記憶體或端到端延遲。測量只覆蓋事件召回 wrapper，固定上游 prompt 是 stub，不含真正故事全組裝、摘要／章節／Canon 內容品質、LLM 提取及生成、供應商 tokenizer、cache usage、費率與帳單。providerTokens/providerCost 保持 null。無額外 API、付費、模型下載或生產資料。沒有實測結果前，不宣稱整體品質或成本改善。

若新排序沒實際改善、發生權限/來源退步或超出預算，不擴大使用範圍；若容量或效能才是主要瓶頸，另案決策，不自動引入向量或擴大索引。正式長篇實測需使用授權合成/自有作品及現有 BYOK 模型、明確 usage 與成本預算；本輪不發出真實請求。
