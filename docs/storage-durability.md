# 本地儲存完整性

## 備援完整性標記（2026-10-17）

IndexedDB 無法寫入時，Storage 仍保留記憶體快取，並嘗試寫入
localStorage。自動存檔和手動槽位使用兩個 key；它們不是同一筆交易。
舊版即使其中一筆因 quota 失敗，也會寫下 `yes` 標記，下次啟動可能
把不完整備援當成完整快照而刪掉原本的 IndexedDB 資料。初始化連資料庫
都無法開啟時，也不能假設空快取代表資料庫中沒有存檔。

目前只有下列條件都成立，備援才能成為下次啟動時的完整快照：

1. 快照源自已載入的 IndexedDB，或已確認完整的新版備援，且有來源版本。
2. 更新任一備援 key 前，先撤銷舊標記；無法撤銷就不變更舊備援。
3. 自動存檔寫入／刪除，以及手動槽位寫入，均成功。
4. 先寫入來源版本，最後才寫入 `complete-v3` 標記；還原時必須與資料庫版本相符。

接管 IndexedDB 前先撤銷舊備援標記；若撤銷失敗，不開始修改資料庫，
避免舊標記日後覆蓋更新的 IndexedDB 存檔。遷移完成後清理備援，也
先撤銷標記才刪除資料 key；若撤銷失敗，
就保留完整備援，避免標記指向已被清空的資料。

資料庫尚未載入時產生的 localStorage 資料會保留，但不會升格為完整
快照；後續本地寫入也維持這個來源狀態。重新取得 IndexedDB 後，以
現有合併規則保留較新的自動存檔與不同 ID 的槽位。

舊 `yes` 標記無法證明當時兩個 key 都寫入成功；`complete-v2` 則缺少
跨分頁版本資訊，兩者都採保守合併。
這可能保留舊版曾刪除的槽位；只有新版完整快照才會明確同步刪除。
既有故事 key、IndexedDB store/schema version 與故事備份格式維持不變；
新增來源版本的備援 key，並在 stories store 加入內部版本紀錄。

## 驗證與範圍

`tests/storage-fallback-integrity-core.cjs` 先重現部分寫入仍被標記為完整
的問題，再以實際 migration policy 驗證重新啟動後保留既有存檔。
覆蓋新舊標記、quota、標記撤銷／寫入失敗、自動存檔刪除失敗、完整
快照的正常刪除，以及資料庫開啟失敗後繼續本地寫入。

交易、初始化和遷移流程另由 `tests/storage-indexeddb-core.cjs` 驗證；
備份、還原及密鑰清理沿用既有回歸。儲存測試均列入 Core CI。

## 初始化與交易失敗復原（2026-10-17）

讀取 IndexedDB 後，先同步把啟動期間累積的全部操作套回快取，再逐筆
持久化。整個重播期間維持 initializing 狀態；此時新增的操作會即時
更新快取並加入同一佇列，後續僅持久化，不重複套用舊操作。
佇列清空後才切換為 indexedDB，避免新舊寫入在兩條佇列間交錯。

若重播任一筆失敗，完整快取已包含最後一次自動存檔、槽位新增和刪除，
因此可依完整備援協定降級；不會因為提前取出整批佇列而漏掉後面的操作。
資料庫尚未成功讀取時仍維持原有的保守備援規則。

交易 action 同步拋錯時，主動 abort 整筆交易，撤銷之前已排入的請求，
並保留原始錯誤供呼叫端處理。

`tests/storage-initialization-recovery-core.cjs` 覆蓋重播期間的新寫入、
第一筆／中途／後段失敗、降級後重新遷移保留刪除，以及交易提交／回滾。
初始化測試控制 I/O 時序；交易測試用暫存修改模擬原子提交與中止，
既有 IndexedDB 測試繼續驗證實際儲存方法的串接。

## 多分頁槽位修改（2026-10-17）

每個分頁持有自己的快取。過去新增／刪除單一槽位，卻依本分頁的整份
槽位清單重寫資料庫，可能刪掉其他分頁的新槽位，或讓已刪除的槽位復活。
現在只 put／delete 操作指定的槽位；同筆 readwrite 交易再讀取修改後的
全部紀錄，依 savedAt 保留最新 20 個槽位。瀏覽器會序列化同一 store 的
寫入交易，因此容量判定也不會依過期快取覆蓋其他分頁的結果。
自動存檔與其他 kind 的紀錄不參與槽位清理。

`tests/storage-multitab-core.cjs` 用共用交易排程模型驗證並發新增、舊快取
刪除、避免復活、容量裁切及重新讀取；`tests/e2e/storage-multitab.spec.cjs`
在實際瀏覽器以兩個分頁驗證同一流程，並確認交易 action 拋錯會回滾。

本次保護 IndexedDB 一般槽位寫入。其他分頁的清單不會即時自動刷新；
重新載入後會取得最新內容。同一槽位 ID 仍以最後提交的操作為準。
自動存檔仍共用一筆紀錄，採最後寫入者覆蓋；初始化遷移和備援的版本檢查見下節。


## 原子遷移與備援來源版本（2026-10-18）

遷移在同一筆 readwrite 交易中讀取目前資料、決定合併結果並寫回，
不再先以另一筆 readonly 交易建立稍後可能過期的快照。沒有待遷移的
本地資料時，不執行重寫。清理備援前比較遷移時的 key 內容；若內容已
改變，就保留新備援，不會因本分頁的舊遷移完成而清掉另一分頁的新資料。

每筆 Storage 的 readwrite 交易在同一 store 更新 `__story_revision__`
內部紀錄（kind 為 storage-meta）。載入快取時記住來源版本；此後只計入
本分頁成功提交的次數，不以其他分頁最新版本「追平」來源，以免掩蓋
快取漏掉其他分頁資料的事實。此紀錄不會列入槽位或故事備份。

完整備援會先寫入 `bao-lab:story-idb-fallback-revision-v1`，成功後才寫下
complete-v3 標記。重新遷移時，在寫入交易內比對目前版本；相符時才
允許完整快照同步刪除。不符、來源版本缺失或使用舊標記時，以較新
自動存檔與槽位 ID 合併；因此衝突時可能保留本分頁原想刪除的槽位。
這是為了避免以舊快照刪除其他分頁已提交的資料。

`tests/storage-migration-concurrency-core.cjs` 控制讀寫交錯，驗證遷移不
覆蓋新自動存檔、不復活已刪槽位；也驗證來源版本相符的正常刪除、
版本衝突保留遠端資料，以及清理時保留已改變的備援。雙分頁瀏覽器
測試覆蓋相同的交易與版本流程。備援測試另涵蓋來源版本寫入失敗。

限制：已開啟的舊版分頁不會寫入版本紀錄，無法提供同等衝突保護；
部署後應重新載入所有分頁。localStorage 的多 key 寫入仍不是跨分頁
原子交易，多個已降級分頁同時更新備援的協調尚待後續處理；自動存檔
平常仍採最後提交者覆蓋。更完整的備份還原壓力測試亦另行安排。
