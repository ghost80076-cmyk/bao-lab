# 事件召回與知情隔離固定驗收

這是 #749–#752 之後的驗收批次，與已結案的 P0–P2 技術債分開。以人工指定 oracle 的合成故事，檢查既有事件索引如何進入實際 `App.buildMessages`；不使用玩家對話、不呼叫模型，也不量測 LLM 提取／理解／生成品質。

## 重現

```sh
node scripts/evaluate-episodic-recall.cjs --report /tmp/recall-acceptance.json
node tests/recall-acceptance-runner-core.cjs
```

[固定案例](../tests/fixtures/recall-acceptance/v1.json) 包含五個小型故事、34 次查詢：角色獨知、傳聞與後來告知、多人不同認知／共同認知、世界模式的在場角色、原文／語意欄位改寫、回退與另一 state、存檔還原、200 輪後的記憶、關係提示與同義詞標籤、已在摘要的精確去重、關閉／完整原文模式、四筆排序上限及無關輸入。所有期望結果都由 fixture 指定，不從演算法決策回填答案。

Evaluator 載入實際 core 與 runtime wrapper，檢查最後一則 user 訊息內真正輸出的條目及來源；不是只看 `included` 回報。另檢查固定／記憶前綴、state 未變、無模型呼叫、四筆與 2,400 字元條目合計上限。條目間分隔符另列於實際輸出字元數，不混入 core 的預算計數。

## v1 修正前後

[修正前結果](recall-acceptance-before.json) 由 #752 合併版本 `e8a0a2837e008d5a5cf5def551f4682b0b4d0577` 的 core 重現；[v1 修正後結果](recall-acceptance-v1.json) 使用修正後 core。兩者使用相同 fixture、runtime 與 evaluator，JSON 記錄四個來源的 SHA-256。

| 指標 | 修正前 | 修正後 |
| --- | ---: | ---: |
| 32 個既有能力案例的條目集合符合 oracle | 31／32 | 32／32 |
| 既有能力案例 micro precision | 95%（19／20） | 100%（19／19） |
| 既有能力案例 micro recall | 100%（19／19） | 100%（19／19） |
| 不應加入的條目 | 1 | 0 |
| 引用了錯誤來源的回憶區塊 | 7 | 0 |
| 指定禁用內容出現在回憶區塊的案例 | 0 | 0 |
| 包含 2 個能力缺口的全部案例 micro recall | 90.5%（19／21） | 90.5%（19／21） |
| 模型呼叫 | 0 | 0 |

Precision = 正確送出條目／所有送出條目；recall = 正確送出條目／oracle 要求條目。按條目累計，不是案例通過率；四筆排序案例的 oracle 是預算政策要求的四筆，不要求所有相關項目都突破上限。分母為零時輸出 null，不算 100%。來源正確性與禁用文字另外統計，不能用命中同一事件掩蓋錯誤引用。

第一個修正是私密角色認知的「來源」改用實際送出 claim 的 knowledge evidence；多人共同認知取這些 claim 的來源聯集。公開事實維持事件本身來源。更正、回退、精確去重後，只引用留下的 claim。

第二個修正是私密回憶排序不再把客觀事件正文作為關鍵字訊號。例如守衛只聽過戒指傳聞，詢問角色未知的「王城密道」不再因客觀正文而觸發該傳聞。既有 entities／keywords 標籤與關係提示仍沿用；這不是模型全域秘密隔離保證，也不是自動判斷所有標籤的知情範圍。

## v1 記錄的兩個能力缺口

- `unknown-alias-gap`：事件記錄「艾琳」，查詢的主要角色為「阿琳」；目前 audience／knowledge 精確匹配沒有統一別名映射，因此漏召回。
- `untagged-paraphrase-gap`：輸入「妳為何不願相信我？」沒有命中事件的關鍵字或既有關係提示；目前沒有語意向量檢索，因此漏召回。

這兩筆 oracle 仍要求相關事件，實測缺失保留於全部案例的 false negative。CI 要求它們只出現 fixture 明列的已知缺失；新增錯召回、禁用內容、來源錯誤或其他既有能力退步一律失敗。若以後補齊能力，先審查更新診斷 oracle 並轉為支援案例，避免把改善偷偷隱藏在舊基線。

Gate 自身有故障注入：空召回、把私密事件當公開、改回錯誤來源都必須讓命令非零退出。CI 也核對目前 report 與 checked-in baseline 一致，防止原始碼已改但證據過期。Actions 保存當輪量測 JSON。

## 驗收界線與後續

目前結果只涵蓋這 34 個確定性合成查詢；不代表玩家實際 recall rate、模型一定遵守知情範圍、端到端秘密隔離或 Token／費用改善。模型提取若把傳聞誤寫為公開事實，這個 fixture runner 不會代替真實提取品質評估。既有摘要、完整歷史、人物卡及其他系統資料亦不在此隔離保證內。

v2 已補上只依已登錄 NPC 身份／別名解析的對應；遇到同名或歧義拒絕私密召回，不從對話提及推定在場或知情。語意檢索應等更大、分離的測試集及成本證據，不能只為通過一個改寫案例增加付費呼叫。正式供應商帳單對帳 O1 仍獨立保留。

## v2：已登錄別名與歧義驗收

#754–#758 已合併後，本批對齊最新主線，保留錢包、SEO、作品及分頁回歸修改。新增 [v2 固定案例](../tests/fixtures/recall-acceptance/v2.json)，保留 v1 fixture 與前後原始報告供比較。

現在只依目前故事 NPC 的正式名稱、aliases 與 npc_id 對應身份。唯一別名可在 audience、事件知情、Canon、世界書和 NPC 私密日程使用同一正式身份；相同身份的正式名與別名不重複計算 speaker。知情記錄仍依有效來源順序選最新內容；原始 actor／known_by／日程資料不做遷移或改寫。

同一別名指向兩人、別名碰到另一人的正式名、或無穩定 ID 的重複同名，皆視為歧義。任何 speaker 有歧義時，整份私密 audience 拒絕；不能刪去該 speaker 後只保留另一個有權人物。歧義 known_by 不提供權限，歧義的舊知情記錄不轉給任一人物。公共資料沿用原規則。未登錄名稱仍保留原本的精確名稱行為，不推測拼字、大小寫、翻譯或語意近似，也不自動把不在場人物帶入世界模式。

[目前 v2 結果](recall-acceptance-baseline.json)：41 個案例，其中 40 個既有／新增能力案例符合 oracle；錯召回、錯來源、指定禁用內容均為 0。全體正確條目 23／24，micro recall 95.8%，剩餘 1 筆無關鍵詞改寫仍是已知缺口。原 alias gap 已轉為一般支援案例；增加別名碰撞、正式名碰撞、整體 cast 拒絕、離場角色、去重及後續認知／回退來源查詢。v1 的 19／21 與 v2 的 23／24 分母不同，不作同分布成效提升宣稱。

新增 `actor-alias-core.cjs` 與 `actor-alias-runtime.cjs`，直接驗證 resolver 與真實 Canon／世界書／事件 wrapper／日程管線，涵蓋歧義、多人、不同 state、來源與零模型呼叫。Resolver 每次操作重建目前 registry，事件召回每次只建一份，避免跨故事快取或逐知情記錄重掃 NPC 名冊。
